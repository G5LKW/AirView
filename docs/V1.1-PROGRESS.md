**Work done**
- `internal/briefing` (new): `Build(Input) *Briefing` writes a daily briefing from `analytics.Daily` (the day and the
  28 days before), `analytics.Top` (the day, 5 rows) and the day's events. Baseline: earlier days with >= 20 h of data,

## 2026-11-27 (run 3) - auto/radar-locate

**Scope.** PRs #1 and #2 are complete and await the owner, so this run took the next ROADMAP item that the unmerged
`claude/zen-davinci-sbmb33` branch does not cover: interrogator radar locating. Stacked on `auto/acars` (PR #2).

**Work done** (ROADMAP "Interrogator radar locating"):
- `internal/mlat/ssr/sweep.go`: `LocateBySweep` locates SSR interrogators from the timing of their beam sweeps. The
  DF11 all-call bursts of each II/SI code arrive while that radar's beam points at the replying aircraft, so
  (aircraft position, burst time) pairs give the site, rotation period and sense by a bearing-only fit: period from
  the periodogram of each aircraft's repeat intervals, site by a windowed circular-coherence grid on the existing
  gnomonic plane (coarse 8 km, refined to 125 m, both senses), robust Gauss-Newton with a phase per 60 s window,
  formal error ellipse. Up to three radars per code (codes are reused). Works in the Mode S lockout case where the
  pair method of SSR-RESEARCH.md finds nothing, and does not need the station position.
- Estimator: keeps the last hour of DF11 bursts with a non-zero code (at most 30000, ~1.7 MB); `LocateRadars`.
- Engine: run at each SSR solve; `GET /api/ssr` gains `radars` and `estimator.sweepBursts`.
- UI: Settings > SSR self-location shows "Radars located from beam sweeps" (code, status/reason, position, formal
  error, rotation with sense, bursts/aircraft, fit, nearest reference site within 25 km).
- Reference data: the nearest `ssr.sites` entry is reported with its distance. No radar list is shipped; the manual
  explains how to enter published sites (Ofcom licence data where it covers the site, or an AIP).
- ssrsim: anticlockwise radars (negative period) no longer crash the simulator.
- `internal/uplink` (found this run): per-receiver side records (INPUT_STATUS, CLOCK_STATUS, GNSS_POS) of a receiver
  that appeared mid-session could precede its RECEIVER record (AVF protocol error at the server); they now wait.
- Docs: manual (Settings > SSR), SSR-RESEARCH.md §9, CLEANROOM provenance, package doc, API summary.

**Tests**
- New: `TestLocateBySweepModeS` (three all-call-only radars, two sharing II 3, one anticlockwise, 50 % lockout:
  located 10, 7 and 26 m from the truth, formal σ_h 6-23 m, periods within 0.3 ms, reference site matched),
  `TestLocateBySweepLockout` (full lockout: nothing reported), `TestLocateBySweepEmpty`, `TestCodeName`,
  `engine.TestSSRWiringSweep` (through the Beast frame decoder and `status()`: 7 m and 11 m), `BenchmarkLocateBySweep`
  (0.4 s for three radars on a 4-core VM core, after cutting the coarse grid to 300 bursts; 0.9 s before).
- `gofmt -l` clean, `go vet ./...` clean, web unit tests pass, `node --check` on the changed module.
- Full `CGO_ENABLED=0 go test -count=1 -timeout 40m ./...` on a 4-core VM: every package passes except the known
  fresh-clone failures (`cmd/airview` missing DB fixture, `deploy/feeder/windows` CRLF that needs a fresh checkout;
  both addressed by PR #1 / the owner) and `engine.TestUplinkTee` once under the parallel load ("session 1: first
  record is INPUT_STATUS, not RECEIVER"). It passed 3x alone and 6x next to six busy loops, so it was not reproduced,
  but the cause is clear from the code: a receiver that appears after the session started gets its RECEIVER record
  in the live queue, while its INPUT_STATUS (side record, due at once because `inputAt` starts an hour back) is
  written first by `pump`. Fixed in `internal/uplink`: INPUT_STATUS, CLOCK_STATUS and GNSS_POS now carry their
  receiver number and wait until that receiver is announced in the session. `internal/uplink` and
  `internal/engine` pass afterwards (TestUplinkTee 3x more). `internal/analytics` 987 s, `internal/mlat/clock` 648 s.
- `-demo` on port 18095 with `-set ssr.enabled=true`: `/api/ssr` answers with `sweepBursts` (0: the demo simulator
  only sends II 0 squitters). Playwright at 375 px and 1440 px on Settings > SSR, with the real response and with a
  mocked `radars` list: the table renders, scrolls inside its card at 375 px, no page-level horizontal scroll, no
  console errors. The "±1σ" header was renamed "Formal error" (the uppercase style turned σ into Σ) and references
  further than 25 km are shown as "none within 25 km".

**Not verified**
- Any real radar: ssrsim's beam is an ideal window, so burst centres are unbiased there. Real errors (beam squint,
  bursts cut by lockout, position latency) are not in the formal ellipse and have not been measured.
- How often real Mode S radars give enough repeat bursts under lockout; Pi 4 run time (expected several times the
  VM figure, on the estimator's own goroutine).
- The demo mode has no rotating radars, so the table was only seen with mocked data.

**Open issues**
- The locator only runs with the experimental `ssr.enabled`; a separate switch is in the backlog.
- Owner actions from PR #1 still open (`cmd/airview/testdata/airview-1.0.0.db`).
